# Melbourne Urban Forest API test matrix

**Prepared by** Darvin Anorma Mangampo

**Planning began** 12 October 2026. **Matrix prepared** 13 October 2026. The eight rows below set out the API test conditions. T05 and T06 have two cases each, so they should appear as about ten test executions in Playwright's HTML report. On 13 October, I used Playwright to make twelve GET requests and examine the fields and responses used in this matrix. The preflight log is kept at `evidence/Milestone-A/preflight-results.json`.

I started this 2026 API testing project as part of my upskilling to apply what I learned in The Test Tribe Playwright course, separate from the work I did in my previous role.

## Basis for expected results

**P** means the [City of Melbourne dataset page](https://data.melbourne.vic.gov.au/explore/dataset/trees-with-species-and-dimensions-urban-forest/information/) or [Explore API reference](https://help.opendatasoft.com/apis/ods-explore-v2/explore_v2.1.html). **O** means observed in the dated preflight and to be checked again during test execution. **R** means this project's rule for comparing two API responses. The [ISTQB Foundation Level syllabus](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf) sections 4.1 and 4.2.2 informed the choice of black-box checks and T05's boundary pair. No client requirements were supplied for this project. Provider documentation supports **P**. A comparison marked **R** checks consistency between responses, while **O** describes what happened in one run. None verifies the accuracy of the underlying tree inventory.

## Eight test conditions

| ID and consumer reason | Request and checks | Expected result and basis | Evidence to retain |
| --- | --- | --- | --- |
| **T01 Availability and shape.** A consumer needs usable tree data. | GET the dataset with `limit=5`. Check status, JSON content type, a non-empty `results` array, numeric `total_count`, and at least one current row with a non-empty `com_id` and `genus`. Do not require every row to have a populated genus. | HTTP 200 with JSON and the documented response shape. The sampled row provides usable fields. **P, O, R** | Status, content type, result count and field names from that row. Tag this small check `@smoke`. |
| **T02 Bounded pagination.** A consumer should not see the same tree on adjacent pages. | GET `limit=5`, `offset=0` and `offset=5`, both ordered by `com_id ASC`. Check five rows on each page, ascending `com_id` order, and no repeated `com_id` across pages. | `limit`, `offset` and `order_by` work as documented. Exact page lengths and distinct IDs are this project's comparison rules for a dataset with at least ten trees. **P, R, O** | Both page lengths, ordered ID sequences and two ID sets. Recheck if live data changed between calls. |
| **T03 Tree lookup consistency.** A tree returned by the API should be findable again. | Take a current row with `com_id` and a non-empty `genus`, query `where=com_id = ...`, and compare both fields. | The lookup returns the same tree with matching `com_id` and `genus`. Query syntax is based on **P**. Cross-response equality is based on **R, O**. | Source and lookup `com_id` and `genus` values. Both matched in the dated preflight. |
| **T04 Genus filter accuracy.** A filter should not include another genus. | Use a populated genus from a current result. GET `where=genus = ...` with a small limit. Require at least one returned row and check every returned row's `genus`. | The result is non-empty and every returned row matches that genus. Filter syntax is based on **P**. Non-empty and exact comparison are based on **R**. | Genus used for the filter, returned row count and all compared values. |
| **T05 Page-size boundary.** A client needs a clear limit. | Read two JSON-driven cases, `limit=100` and `limit=101`. Check statuses, JSON and returned-row count or error. | `100` succeeds with at most 100 rows. `101` returns HTTP 400 JSON. The maximum of 100 comes from **P**. Statuses and error shape were observed in **O**. | Two case results and the provider limit. This is one boundary pair, not a full boundary analysis. |
| **T06 Invalid query fields.** A client needs an understandable error for a bad field. | Check two cases, an unknown field in `where` and an unknown field in `order_by`. Check HTTP status, JSON and an error message identifying the field or clause. | Both returned HTTP 400 JSON in the 13 October preflight. This comes from **O**. The valid query-field mechanism comes from **P**. | Separate responses and error messages. Investigate changed behaviour before calling it a defect. |
| **T07 Dataset total comparison.** A consumer may see two total values. | In one run, compare `total_count` from unfiltered tree data with `metas.default.records_count` from metadata. Save both numbers. | The totals agree when the dataset does not change between requests. The fields come from **P, O**. Equality is this project's rule **R**. | Both response values and run time. Investigate a mismatch for a change in live data. |
| **T08 Unknown tree ID.** A missing ID should be handled without a script failure. | Query an unused, well-formed `com_id` such as `999999999`. Check status, empty `results` and `total_count=0`. | HTTP 200 JSON with an empty result was observed in the 13 October preflight. **O** | Status, zero count and empty array. |

## Observation outside the eight conditions

The 13 October preflight returned HTTP 200 at `offset + limit = 10000` and HTTP 400 at `10001`. The provider reference says the sum should be less than 10,000. I noted the difference between the published limit and the response at exactly 10,000 as a dated observation. T05 covers the separate `limit=100`/`101` page-size pair.

The saved preflight log shows a true filter comparison and no repeated IDs, but it does not retain the filtered row count or second-page row count. T02 and T04 make those checks explicit. The preflight flags alone do not prove that both responses contained rows. The full suite should make fewer than twenty read-only requests per run. Assertions will check values and relationships, not only status codes. No current tree total is hard-coded. If an assertion fails, I compare the saved request and response with the cited provider rule or this project's comparison rule, then check whether the live data changed. A difference from a preflight-only observation is not a confirmed provider defect.
