# Melbourne Urban Forest API findings and observations

## Milestone-B baseline observations

**Project owner** Darvin Anorma Mangampo

**Run reviewed** 15 October 2026 (UTC+08:00)

On 15 October 2026, I used Playwright on my computer to run the eight conditions in the [test matrix](test-matrix.md). The eight matrix conditions produced ten Playwright test cases in the 15 October run because T05 and T06 each used two inputs. T01–T04, T07 and T08 ran once each. I began T05 with `limit=100` because it is the published page-size maximum. I then used `limit=101` to see how the API responded to a request beyond it. T06 used an unknown field in `where` and then in `order_by`. All ten test cases passed. The suite made 13 GET requests. Ten returned HTTP 200, and the three deliberately invalid requests returned HTTP 400. All eight conditions passed on 15 October because the checked responses met the expectations I set in the matrix. The separate 10,000 paging observation below was outside those eight conditions.

T01 returned HTTP 200 JSON with five tree rows, a numeric `total_count` and a row with populated `com_id` and `genus`. The Milestone-A log saved HTTP 200 for the genus filter and second page, but not their row counts. Those counts mattered because HTTP 200 can still come with an empty result, as T08 showed. T02 and T04 checked whether the pages and filter actually contained trees. Both sorted pages contained five trees, with ten distinct `com_id` values across them. The `Ulmus` filter returned five trees, and each returned genus was `Ulmus`. These rows and counts describe what the API returned on 15 October. I include the date because the City can update its published tree data. A later request may return different rows or a different total.

The [saved test evidence](Milestone-B/test-evidence.json) retains the T01 sample fields and values, both ordered ID lists and ID sets checked in T02, and each genus value checked in T04. It also retains request paths, response statuses and selected response values for the other conditions. The City of Melbourne [defines `com_id` as a text field](https://data.melbourne.vic.gov.au/explore/dataset/trees-with-species-and-dimensions-urban-forest/). T02 compared the ten returned IDs as text. T02 passed for the ten returned IDs, which all had seven digits. I checked them as text because Melbourne defines com_id as a text field. Text and numeric order can differ when ID lengths differ, so this sample does not establish how every possible ID would sort.

The unfiltered data response and dataset metadata each reported 82,064 trees during the run. Both counts came from the same City dataset, so their agreement shows that the two API responses were consistent during this run. I checked small API responses rather than every tree entry because this suite examines API behaviour through a few read-only requests. Matching totals cannot verify the accuracy of individual entries. I did not compare the dataset with a separate tree list because checking inventory completeness was outside the eight test conditions. The run therefore cannot establish whether every tree is represented. The [City dataset page](https://data.melbourne.vic.gov.au/explore/dataset/trees-with-species-and-dimensions-urban-forest/) lists a monthly source-data update frequency, so a later total may differ. For ungrouped requests to the data endpoint, the [Explore API reference](https://help.opendatasoft.com/apis/ods-explore-v2/explore_v2.1.html) limits a page to 100 results, restricts deep paging and points to exports for larger result sets. I did not use an export because T01–T08 checked specific API requests rather than every published entry. An export could support a separate review of the published list. It would still need an independent inventory to establish whether every physical tree was represented.

In Milestone-A, I checked the 10,000 paging boundary. With `limit=100` and `offset=9900`, the API returned HTTP 200 and 100 rows. Increasing the offset to 9901 returned HTTP 400 with an error saying the sum must be no greater than 10,000. The [City of Melbourne API specification](https://data.melbourne.vic.gov.au/api/explore/v2.1/swagger.json) advises that the sum should be less than 10,000, while the service accepted exactly 10,000 in my check. I kept this deep-paging check outside the eight conditions because I built the suite around the small-page consumer workflow. T02 checked the first two five-row pages. T05 checked the separate page-size boundary at limit=100 and limit=101. All ten test cases passed. I had checked the 10,000 deep-paging boundary during the Milestone-A preflight, but kept it outside T01–T08 because those conditions focused on the first two small pages and the separate 100/101 page-size boundary. The 15 October result therefore adds no new evidence about the difference between the preflight response and the published guidance.

The [saved HTML report](Milestone-B/html-report/index.html) shows each test outcome. The [run summary](Milestone-B/baseline-run-summary.json) gives the date, command, tool versions and overall result. It also keeps hashes of the source files used for this run, including the package file. The [test evidence](Milestone-B/test-evidence.json) preserves the values I checked, including both page ID lists and the five returned genus values.

## Milestone-C repeat run observations

**Run reviewed** 16 October 2026 (UTC+08:00)

On 16 October, I ran T01–T08 again. Repository commit `1ed2bc338de6895b618aa82ca5cede3fc4a36e98` was already present when the run began. All ten Playwright test cases passed. All eight matrix conditions ran. T05 and T06 each had two input cases. T01–T04, T07 and T08 each had one test case. T05 had a case for limit=100 and another for limit=101. T06 had one case for the unknown field in where and another for the unknown field in order_by. Those are ten test cases in the 16 October run, covering the eight matrix conditions. The suite made 13 GET requests. One setup request selected a current tree, and T02 and T07 each needed two responses to compare. Ten requests returned HTTP 200. The request above the page-size limit and the two invalid-field requests returned HTTP 400 JSON. I included three invalid-input cases because I wanted to check whether the API rejected those requests and explained why. For these cases, HTTP 400 JSON was the expected response. T05 also checked that its message referred to limit. Each T06 case checked that its message mentioned the unknown field or the relevant query clause. All three cases passed those checks. All eight conditions passed again on 16 October because the checked responses met the expectations I set in the matrix. The [HTML report](Milestone-C/html-report/index.html) shows each outcome. The [run summary](Milestone-C/repeat-run-summary.json) lists the command and source identity, while the [test evidence](Milestone-C/test-evidence.json) saves the checked request and response values.

T01's five-row response saved a sample with `com_id` 1023218 and genus `Platanus`. A separate setup request supplied `com_id` 1013381 and genus `Ulmus` for the lookup and filter checks. That explains why the T01 sample and T03 source tree have different genus values. The two sorted pages each held five trees. Their ten `com_id` values were in ascending text order without a duplicate. The lookup matched the source ID and genus. All five rows returned by the `Ulmus` filter had that genus.

The API returned HTTP 200 and 100 rows when T05 requested limit=100. It returned HTTP 400 JSON for limit=101 because that request exceeded the published page-size maximum. T06's separate errors identified the unknown field in `where` and in `order_by`. The unfiltered data response and metadata both reported 82,064 trees. For T08, the suite looked up the unused com_id. The API returned HTTP 200 with total_count=0 and an empty results array. I expected an empty result because the 13 October preflight had returned HTTP 200 with no rows for that ID, and I used that observation as T08’s expectation in the matrix. I compared the detailed evidence with Milestone-B. All 13 saved request paths and response summaries match, including the statuses and selected values. I ran the Playwright suite on 15 and 16 October because I wanted to see whether the eight matrix conditions still met their expectations on the second date. The test code sent the API requests when I ran it. I did not run continuous checks between those dates. The tree data could have changed and then returned to the same sampled values before the second run. Matching responses therefore cannot show what happened throughout that interval.

The [Milestone-C test evidence](Milestone-C/test-evidence.json) retains the T01 fields, both T02 ordered ID lists and sets, and the source and lookup values for T03. It also keeps every genus compared in T04. The separate T05 and T06 responses are there, as are the T07 totals with their observation time and T08's empty result. I kept those values because they show the actual IDs, genus values and error messages returned during the run. The five source-file hashes match the Milestone-B summary, showing identical content in the tested files. The baseline summary has no commit ID at execution because its source was committed afterward. The Milestone-C summary names the commit already present on 16 October. Matching hashes do not prove that the API or its data stayed unchanged between the dates.

The equal totals show agreement between two responses from the same published dataset on 16 October. I checked small API responses because the eight conditions focus on read-only consumer behaviour. I did not inspect every tree entry or compare the published list with a separate inventory. This result therefore cannot establish whether every physical tree is represented or each entry is correct. The [Explore API reference](https://help.opendatasoft.com/apis/ods-explore-v2/explore_v2.1.html) caps ordinary ungrouped pages at 100 rows and points to exports for larger retrieval. No export was needed for these conditions.

The 16 October run did not test `offset + limit = 10,000`. T02 used nearby five-row pages, and T05 tested the separate 100/101 page-size limit. Neither reaches the deep-paging boundary from Milestone-A, where the service accepted a request the [published guidance](https://help.opendatasoft.com/apis/ods-explore-v2/explore_v2.1.html) says should be below 10,000. The 13 October preflight returned HTTP 200 when offset + limit equalled 10,000. The published API guidance says that sum should be less than 10,000. I kept this deep-paging boundary outside T01–T08 because the complete suite checked small-page navigation and the separate page-size limit. The two passing runs add no further result at the 10,000 boundary, so I keep the difference as a dated Milestone-A observation. They also do not establish uninterrupted service availability between the run dates.

I describe my work as repeat execution because it compares the same checks on two dates without evaluating such a change.
