# Milestone-B findings and observations

**Project owner** Darvin Anorma Mangampo

**Run reviewed** 15 October 2026 (UTC+08:00)

On 15 October 2026, I used Playwright on my computer to run the eight conditions in the [test matrix](test-matrix.md). Playwright reports ten test executions because two of the eight matrix conditions each have two input cases. T01–T04, T07 and T08 ran once each. I began T05 with `limit=100` because it is the published page-size maximum. I then used `limit=101` to see how the API responded to a request beyond it. T06 used an unknown field in `where` and then in `order_by`. All ten executions passed. The suite made 13 GET requests. Ten returned HTTP 200, and the three deliberately invalid requests returned HTTP 400. Every assertion in T01–T08 met its matrix expectation on that date, so I did not prepare a provider defect report from this run. The separate 10,000 paging observation below was outside those eight conditions.

T01 returned HTTP 200 JSON with five tree rows, a numeric `total_count` and a row with populated `com_id` and `genus`. The Milestone-A access log showed that the genus-filter and second-page requests succeeded, but it did not save their returned-row counts. Both sorted pages contained five trees, with ten distinct `com_id` values across them. The `Ulmus` filter returned five trees, and each returned genus was `Ulmus`. These are results from this run of the live dataset, not fixed facts about the dataset.

The [saved test evidence](Milestone-B/test-evidence.json) retains the T01 sample fields and values, both ordered ID lists and ID sets checked in T02, and each genus value checked in T04. It also retains request paths, response statuses and selected response values for the other conditions. The City of Melbourne [defines `com_id` as a text field](https://data.melbourne.vic.gov.au/explore/dataset/trees-with-species-and-dimensions-urban-forest/). T02 compared the ten returned IDs as text. T02 passed for this sample. It does not establish how every possible text ID would sort, so a later sample with different ID lengths would need to be judged on its own returned order.

The unfiltered data response and dataset metadata each reported 82,064 trees during the run. Both counts came from the same City dataset, so their agreement shows that the two API responses were consistent during this run. I checked small API responses rather than every tree entry because this suite examines API behaviour through a few read-only requests. Matching totals cannot verify the accuracy of individual entries. I did not compare the dataset with a separate tree list because checking inventory completeness was outside the eight test conditions. The run therefore cannot establish whether every tree is represented. The [City dataset page](https://data.melbourne.vic.gov.au/explore/dataset/trees-with-species-and-dimensions-urban-forest/) lists a monthly source-data update frequency, so a later total may differ. For ungrouped records requests, the [Explore API reference](https://help.opendatasoft.com/apis/ods-explore-v2/explore_v2.1.html) limits a page to 100 results, restricts deep paging and points to exports for larger result sets. I did not use an export because these checks did not require the entire dataset.

In Milestone-A, I checked the 10,000 paging boundary. With `limit=100` and `offset=9900`, the API returned HTTP 200 and 100 rows. Increasing the offset to 9901 returned HTTP 400 with an error saying the sum must be no greater than 10,000. The [City of Melbourne API specification](https://data.melbourne.vic.gov.au/api/explore/v2.1/swagger.json) advises that the sum should be less than 10,000, while the service accepted exactly 10,000 in my check. I kept this deep-paging check outside Milestone-B's eight conditions. The suite checked tree data and two nearby five-row pages. T05 covered the separate 100/101 page-size pair. All ten executions passed, but none tested the separate deep-paging boundary where `offset + limit = 10,000`. This run therefore does not resolve the difference observed in Milestone-A between the published guidance and the API response at that boundary.
