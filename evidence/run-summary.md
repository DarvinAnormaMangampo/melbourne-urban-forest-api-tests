# Melbourne Urban Forest API run summary

**Prepared by** Darvin Anorma Mangampo

In my [test plan](test-plan.md), I set out two complete runs on different dates. All eight matrix conditions ran on both dates. T05 and T06 each had two input cases. Each of the other six had one, which gave Playwright ten test cases per complete run. All ten passed on both dates, with no failures or skips. Each run sent 13 GET requests. T01 used two requests because setup fetched a current tree and the check sampled another five-row response. T02 fetched two pages. T07 fetched data and metadata separately. The other seven cases made one request each. Both runs had the same case and request counts. Three of the 13 requests deliberately used invalid input. Their HTTP 400 responses counted as passes only when the expected error details were present. I ran the same checks on a later date because I wanted to see whether their sampled requests still met the matrix expectations. I had not identified a City API change as the subject of this comparison. These results compare two dated executions, so they do not measure the effect of a particular service change.

I compared the two detailed test-evidence files as well as the pass counts. All 13 saved request paths and response summaries match, including their statuses and selected values. Each T07 entry saves when I compared the data total with the metadata total. The Milestone-C time is later because I ran that comparison again on 16 October, after the 15 October baseline. Both entries report 82,064. I ran the Playwright suite on each date because I wanted to compare the same eight checks. Once I started each run, Playwright sent the API requests defined in the test specification. I kept the returned values in the detailed evidence for comparison. I did not monitor the API between those runs. A tree entry could have changed after the 15 October run and been restored before I tested again on 16 October. The service could also have been unavailable briefly and recovered. Because I made no requests between the runs, matching responses cannot rule out either possibility.

The B summary lists the command `node ../../../node_modules/@playwright/test/cli.js test --config playwright.config.ts --reporter=list,html`. The C summary lists the command entered from the repository root as `node node_modules/@playwright/test/cli.js test --config playwright.config.ts --reporter=list,html --trace=retain-on-failure --output $testResultsPath`. In that PowerShell session, `$testResultsPath` pointed to the designated output folder. The different `../` prefix in the B command reflects the folder from which that command was entered, not a different test specification. These are the commands that produced the saved results. The [Milestone-C README](Milestone-C/README.md) shows how to install the dependencies and run pnpm test from a clone.

Both runs used one worker with parallel mode and retries disabled. The test code paced the 13 GET requests by 700 ms each. The saved summaries list Node.js 24.19.0 and Playwright 1.64.0 for both executions. They also list pnpm 11.25.0 as available. The displayed commands invoke Playwright through Node.js. Neither complete run received HTTP 403 or HTTP 429, and I encountered no access challenge. I had set these as reasons to stop because I did not want to continue sending requests after the public service restricted access.

In the [test plan](test-plan.md), I set out all eight matrix conditions and two complete runs on different calendar dates. Each HTML report shows ten case outcomes because T05 and T06 each used two inputs. The [Milestone-B](Milestone-B/test-evidence.json) and [Milestone-C](Milestone-C/test-evidence.json) detailed evidence each keep the ordered ID lists from T02. They also keep every genus value checked in T04 and the two totals compared in T07. I specified those values in the matrix because I wanted to check what each assertion compared and whether the same values appeared on the later date. Section 5.1.3 of the [ISTQB Foundation Level syllabus](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf) informed my review of the plan's completion criteria. The source identification difference between the runs is explained above.

The repeated passes show that the sampled requests met their assertions on each date. T07 compared two counts from the same dataset, so matching 82,064 totals do not independently verify the physical tree inventory. Neither run inspected every entry, and neither shows whether the service was available continuously between dates. During the 13 October Milestone-A preflight, I requested limit=100 with offset=9900. The API returned HTTP 200 when their sum reached 10,000, although the published guidance says the sum should be below 10,000. When I defined the eight automated conditions, I included checks for two nearby five-row pages in T02 and for the 100/101 page-size boundary in T05. I did not include a check of the separate 10,000 deep-paging boundary. I ran those same eight conditions on 15 and 16 October, but I did not repeat the deep-paging request separately. That was a scope choice, not something that being a preflight request prevented. Because neither later run requested limit=100 with offset=9900, I have no later response showing whether the API would again return HTTP 200 for it. The 13 October response remains a dated observation that the two complete runs did not verify again.
